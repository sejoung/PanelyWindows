# ADR 0009: 읽는 동안의 비용을 줄이고, 메모리 예산을 실제로 지키며, 쓰지 않는 번역 모델은 내린다

- 상태: 채택(2026-11-02 Windows에서 `verify.cmd`와 앱 실행으로 동작 확인. 성능 측정은 아직, 아래 "결과" 참고)
- 날짜: 2026-11-01
- 보완: [ADR 0008](0008-gemma-translator.md) 7·8번(모델을 올린 뒤 앱 종료까지 유지하던 것을 유휴 해제로 바꾼다)
- 관련 코드: `ReaderSession.SetPage`·`FlushPositionInBackground`, `MainWindow.RefreshSidebarSoon`·`LoadBookmarkThumbnail`, `LibrarySidebar.SetData`, `PageImageCache.Evict`·`Post`, `ThumbnailPanel.RequestThumbnail`, `SourceMonitor.Watch`, `ExtractionCache.Enforce`·`DetachStaleStaging`·`FinishOrphanCleanup`, `StateStore.Flush`, `TranslationScheduler.RunLoopAsync`·`CachedPages`, `IIdleReleasable`, `IReaderHost.InvalidatePageOverlay`
- 테스트: `PerformanceGuardTests.cs`

## 배경

전체 코드를 읽어 성능을 검토했더니(프로파일링 없이 코드 검토로 찾았다) 가장 자주 쓰는 경로에 낭비가 있었다.

- 쪽을 넘길 때마다 사이드바를 통째로 다시 만들었다. 숨겨져 있어도 그랬고, 현재 책의 북마크마다 원본을 읽어 썸네일을 새로 디코드했다. ZIP·RAR에서는 이 작업이 쪽 디코드와 같은 아카이브 핸들을 기다려 볼 쪽이 늦어졌다.
- 코드 주석은 "keep 안이라도 예산을 넘으면 버린다"고 했지만 keep 범위 밖만 제거했다. 4000×6000 쪽(장당 96MB) 21장이면 상한 1GiB를 넘는다.
- UI 스레드에서 디스크를 만졌다. 책을 바꿀 때 상태 저장(fsync), 폴더 전체 열거, 캐시 정리를 했고, 시작할 때 남은 임시 폴더를 지웠다.
- 번역을 마친 뒤에도 Gemma와 ONNX 세션이 앱을 닫을 때까지 RAM·VRAM에 남았다.

## 결정

1. 쪽 이동은 `ReaderChange.Bookmarks`를 올리지 않는다. 쪽 이동은 북마크 목록을 바꾸지 않고, 툴바 표시는 `Page` 변경에서 갱신된다.
2. 사이드바는 보일 때만 갱신한다. 숨겨져 있으면 표시만 해 두고 열 때 맞춘다. 진행률 변경은 약 1초로 묶고, `SetData`는 이전 값과 비교해 이어보기 진행률만 바뀌었으면 그 행만 바꾼다.
3. 이어보기·북마크 섹션과 파일 트리를 다른 패널로 나눈다. 위쪽이 바뀌어도 트리를 뗐다 붙이지 않는다.
4. 북마크 썸네일은 책 안에서 쪽마다 한 번만 만들고 동시에 2개까지 읽는다. 책이 바뀌면 취소한다.
5. 이미지 제거 순서는 keep 밖 LRU → keep 안에서 현재 쪽과 먼 순서다. 최근 요청한 쪽(보이는 쪽과 인접 프리로드)은 제거하지 않는다. 제거하면 세로 모드에서 스크롤 이벤트마다 같은 쪽을 다시 디코드하기 때문이다. 그래서 이 쪽들만으로 예산을 넘으면 잠깐 초과할 수 있다.
6. 세로 모드 치수 결과는 80ms씩 묶어 게시한다. 게시마다 전체 배치를 다시 계산해 쪽 수의 제곱으로 비용이 늘었다.
7. 썸네일은 최근 요청부터 처리하고 대기는 64개까지 둔다. 넘치면 가장 오래된 요청을 버린다. 그 셀이 다시 보이면 다시 요청된다.
8. 책 전환 때 상태 저장은 worker에서 하고, 새 책을 화면에 올리기 전에 끝을 기다린다. 앱 종료 때는 지금처럼 동기로 저장한다.
9. 폴더 책의 감시 시작(`SourceMonitor.Watch(OpenedBook)`)은 worker에서 한다. 그 사이 다른 책으로 바뀌면 요청을 건너뛴다. 기준값을 만들기 전에 일어난 변경은 알리지 못할 수 있다.
10. 해제 캐시는 잠금 안에서 entry를 `trash/`로 옮기기만 하고 삭제는 잠금 밖에서 한다. 파일 읽기도 잠금 밖에서 한다. 앱은 `EnforceInBackground`를 켜서 lease 해제 뒤의 정리를 worker에서 한다.
11. 시작 때는 남은 staging을 먼저 `trash/`로 옮기고(이름 변경이라 빠르다) 삭제는 백그라운드로 보낸다. 그냥 백그라운드로 보내면 실행 인자로 바로 연 책의 staging까지 지울 수 있다.
12. `state.json`을 들여쓰기 없이 쓴다. 저장 중에 상태 잠금을 잡으므로 크기와 직렬화 시간을 줄인다. 읽는 쪽은 그대로 호환되고 `SchemaVersion`은 올리지 않는다.
13. 번역 작업과 짧은 번역이 `IdleModelRelease`(10분) 동안 없으면 번역·탐지·OCR 모델을 내린다(`IIdleReleasable`). 책을 읽으면서 번역을 다시 쓰지 않는 경우가 많고, 모델이 수 GB를 차지하기 때문이다. 유휴는 대기 시간이 아니라 마지막 사용 시각으로 잰다. `_signal`은 쪽을 넘길 때도 오므로 대기 시간으로 재면 읽는 동안 내려가지 않는다.
14. 오버레이는 내용이 바뀐 쪽만 무효화한다. 작업 진행 알림에서는 무효화하지 않는다. 드래그 선택 중에는 풍선 그림을 재사용하고 선택 사각형만 새로 그린다.

## 고려했지만 하지 않은 것

- **파일 트리 가상화**: 사이드바 전체가 한 스크롤 영역이라 트리 높이가 제한되지 않아 가상화가 동작하지 않는다. 구조를 바꿔야 해서 화면 확인 없이 하지 않았다. 항목이 수천 개인 폴더를 처음 펼칠 때는 여전히 느릴 수 있다.
- **위치·진행 데이터를 `state.json`에서 분리**: 저장 형식이 바뀌고 옮기기(migration)가 필요하다. 12번으로 먼저 줄이고 실측 후 판단한다.
- **표시 크기에 맞춘 축소 디코드**: 확대하면 다시 디코드해야 한다. 5번으로 상한을 지키는 쪽을 택했다.

## 결과

- 측정한 것은 텐서 입력 채우기(960×960, macOS 벤치마크) 하나다. 인덱서 19.4ms·116MiB에서 `Buffer.Span` 3.2ms·10.5MiB로 줄었다. 절대값은 Windows PC와 다르다. PP-OCR 줄 탐지 실측(`OcrRuntimePolicy` 주석의 139ms/상자)에서 전처리 비중이 크지 않아 번역 전체가 눈에 띄게 빨라지지는 않을 것이다.
- **나머지 효과(쪽 넘김 지연, 메모리, 책 전환)는 측정하지 않았다.** 이 변경은 macOS에서 작성했고, 2026-11-02에 Windows에서 `verify.cmd`를 통과했다. 사이드바 갱신(고정·숨김), 원본↔번역 전환, 저장 공간 탭, 파일을 옮긴 뒤 경로 갱신은 실제 앱을 UI Automation으로 조작해 확인했다. 유휴 모델 해제는 자동 테스트(가짜 공급자)로만 확인했다.
- 번역을 한동안 쉬었다가 다시 시작하면 모델을 다시 올린다(GPU에서 셰이더 준비 포함 약 20초, 분석과 겹쳐 돈다).
- `state.json`을 직접 열어 보기는 불편해진다.
- 썸네일이 처음 화면에서 아래쪽부터 채워질 수 있다.
